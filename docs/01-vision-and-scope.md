# 愿景、范围与设计原则

> **文档角色**：产品宪章与最高层系统边界
> **权威性**：已确认产品决策；改变玩家权限或核心原则前必须更新
> **何时阅读**：新增大系统、处理范围争议、改变玩家角色或外部系统边界时
> **可跳过**：语义明确的局部实现、样式、测试或构建改动
> **相关代码**：全局约束；当前战斗入口主要为 `src/App.tsx` 与 `src/sim`

## 1. 产品目标

系统需要呈现一个能够自行运转的俯视角战场。多个势力从各自出生区域进入地图，在有限情报条件下侦察、判断、机动、交火、撤退并达成模式目标。

玩家的主要乐趣来自观察战局形成和理解单位行为，而不是进行即时微操。因此，系统必须同时满足：

1. 单位行为具有可解释的战术原因。
2. 不同兵种能通过能力和地形自然形成差异。
3. 小型战斗有细节，大型战斗仍能在网页端运行。
4. 战斗结果可以被外部战役、编制、英雄和成长系统使用。

## 2. 玩家角色

正式战斗中，玩家只拥有观察权限：

- 暂停和继续演算。
- 移动、缩放、旋转或切换摄像机模式。
- 选择单位、目标与区域查看信息。
- 在全知视角和某个势力的情报视角间切换。
- 切换战术信息 UI 与纯净观察 UI。

玩家不能在战斗中：

- 选择或移动部队。
- 指定攻击目标。
- 改变阵型、姿态或技能释放时机。
- 临时修改外交关系或战斗目标。

开发调试工具可以暂停、单步、调整速度或注入场景事件，但这些能力不属于正式玩家规则。

## 3. 外部系统边界

战斗模块不负责决定玩家拥有哪些部队，也不负责战役层配置。外部系统通过 `BattleSetup` 传入：

- 地图或地图生成请求。
- 参与势力与外交关系。
- 编组模板、成员、装备、英雄及持久化标识。
- 初始出生区域和增援批次。
- 模式、目标、时限和胜负规则。
- 初始情报、作战条令与环境参数。

战斗模块输出事件流和 `BattleResult`，包括：

- 胜方、败方、平局或僵局原因。
- 每名成员的最终伤亡状态。
- 每个平台的部件、乘员和存续状态。
- 撤离、失散、剩余弹药接口值及能力状态。
- 目标占领过程、关键事件和统计摘要。

## 4. 完整目标范围

### 4.1 战场与地图

- 正方形网格和八方向移动。
- 量化但细致的高度、平滑 3D 地形及高低差战术。
- 草地、沙地、泥地、岩石、浅水、深水、沼泽、山脉等组合地形。
- 树木、岩石、墙体、建筑、战壕等静态障碍与掩体。
- 参数化、可复现的随机地图生成。
- 出生区域、增援入口、撤离出口和防守目标区域。

### 4.2 单位与战斗

- 固定编制但底层支持混编的步兵小队。
- 轮式车辆、履带车辆、坦克、运输车和地图内炮兵。
- 直升机、悬停无人机及固定翼任务接口。
- 实际成员减员、载具乘员岗位和简化部件损伤。
- 近战、远程、直接射击、间接射击和范围武器。
- 换弹、压制、士气、简化体力、撤退和重新集结。
- 数据驱动的自动能力和英雄单位。
- 多时代内容兼容，不在核心中规定时代间平衡。

### 4.3 AI 与模式

- 势力级、编组级、成员/武器级三层 AI。
- 有限情报、通信延迟、最后已知位置与搜索行为。
- 冲突模式：侦察、寻找并消灭或驱逐敌对有效战力。
- 防守模式：防守方布防，进攻方侦察、压制并占领目标区。
- 敌对、中立、同盟关系及延迟情报共享。
- 可配置作战条令，首版使用统一默认条令。

## 5. 明确不进入首版的内容

以下内容重要，但只预留接口：

- 地形和掩体损毁。
- 有限备用弹药、复杂补给与运输链。
- 动态天气、昼夜变化及其实际修正。
- 地图外炮击和完整固定翼持续模拟。
- 战斗中自动外交变化、背叛或投降。
- 战斗回放 UI、时间轴跳转和中途存档。
- 移动端触控与性能适配。
- 服务端权威模拟和多人同步。

地图内炮兵、载具、空军和英雄属于完整目标，但应按实施路线分阶段加入，不能阻塞最早的步兵自动交战闭环。

## 6. 设计原则

### 6.1 自动但可理解

AI 的决策必须能够用少量原因解释，例如“前方火力过强，转向侧翼”“目标情报过期，前往最后已知位置搜索”。随机行为必须受明确规则约束，不能成为掩盖决策缺陷的手段。

### 6.2 延长交火而不制造生命海绵

步兵承受较长时间交火主要依靠低暴露、掩体、压制、射界变化和战术移动。无遮挡的近距离火力仍然危险。成员生命值只用于表达伤势过程，不应让普通士兵连续承受大量直接命中。

### 6.3 逻辑精确，表现轻量

编组负责昂贵的 AI 与寻路；成员和载具保留独立状态及视觉位置，但不运行完整 AI。高速小型弹药按射击事件结算，慢速或范围弹药才创建逻辑飞行体。

### 6.4 数据驱动而非名称驱动

核心逻辑只理解移动能力、传感器、武器、护甲、岗位、能力和标签。它不应出现“如果是狙击手”或“如果是未来坦克”一类散落判断。

### 6.5 模块隔离

- 地图生成器只输出标准地图。
- 战斗核心只消费输入并产生状态和事件。
- 客户端只呈现状态并发送暂停等合法控制。
- 外部游戏系统负责持久化、配兵、成长和战役结果。

### 6.6 可复现

模拟使用固定步长、稳定迭代顺序和带命名流的种子随机数。相同版本、输入和种子应产生相同逻辑结果。渲染粒子和镜头可以使用非确定性随机，因为它们不影响战斗。

## 7. 目标规模

规模是性能预算，不是模式规则：

| 预设 | 地图建议 | 战术编组 | 可视成员/平台 |
| --- | --- | --- | --- |
| 小型 | `128 x 128` 格，约 `512m x 512m` | 20～50 | 200～500 |
| 中型 | `256 x 256` 格，约 `1.0km x 1.0km` | 50～200 | 500～2000 |
| 大型 | `512 x 512` 格，约 `2.0km x 2.0km` | 200～500 | 2000～5000 |

首要目标是常见桌面设备上的稳定体验。大规模上限必须通过压力测试确认，不能仅根据渲染实例数量估算，因为有限视野、寻路和 AI 通常比几何体绘制更早成为瓶颈。

## 8. 战斗核心的运行环境

模拟核心使用不依赖浏览器 API 的纯 TypeScript 编写：

- 浏览器中运行在 Web Worker。
- 测试中可直接在 Node.js 执行无界面模拟。
- 未来可迁移到 Node.js 服务端或批量演算进程。

首版不实现多人或服务端运行，但不得在领域代码中引用 DOM、React、Three.js、`requestAnimationFrame` 或系统时间。
