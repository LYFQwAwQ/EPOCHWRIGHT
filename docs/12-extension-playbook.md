# 系统扩展手册

> **文档角色**：新增能力时的跨层实施步骤
> **权威性**：工程操作指南；领域语义仍以 `01-07` 为准
> **何时阅读**：实际新增地形、掩体、兵种、载具、模式、关系、增援、能力、事件或消息时
> **可跳过**：修复既有行为、纯重构、文案和构建维护
> **相关代码**：随扩展类型变化；先用本文件选择必须修改的边界

本文把常见扩展拆成可执行步骤。目标是避免“类型加了字段，但 AI、结果、Worker 或 UI 没有接上”的半成品。

## 1. 通用扩展顺序

任何跨模块能力都按以下顺序推进：

1. **定义行为事实**：明确输入、状态、事件、结果和不变量。
2. **修改公共契约**：只公开跨边界真正需要的数据。
3. **验证与初始化**：拒绝非法组合，并提供确定默认值。
4. **实现纯规则**：优先提取可直接测试的计算。
5. **接入 tick 管线**：明确发生顺序和与现有规则的交互。
6. **加入哈希和结果**：确保复现与外部持久化完整。
7. **增加观察投影**：在 `RenderFrame`、事件或 inspection 中选择合适通道。
8. **接入 Worker 和客户端**：只有契约变化时才改协议。
9. **实现表现与 UI**：不在此层复制规则。
10. **场景回归和文档**：覆盖成功、失败、边界与终止路径。

若某一步暂不实现，应保持功能不可启用，而不是返回看似可用的占位状态。

## 2. 选择数据通道

| 需求 | 使用 |
| --- | --- |
| 每个渲染帧都要显示的位置、姿态或摘要 | `RenderFrame` |
| 已发生且需要短暂表现或记录的事实 | `BattleEvent` |
| 仅在选中实体时需要的详细信息 | `EntityInspection` |
| 战后城市、养成或世界系统必须持久化的信息 | `BattleResult` |
| 仅影响未来模拟决策的内部状态 | `internal.ts` + state hash |

不要为了一个选中面板字段扩大全量高频帧，也不要用瞬时事件代替当前状态。

## 3. 新增地形

例如沙地、浅水、深水、沼泽：

1. 在 `BattleMap` 增加标准化地形图层或 terrain ID，不复用颜色或高度编码。
2. 为地图 schema 定义合法值、默认值和版本策略。
3. 在生成器中按独立 seed 流生成，并验证出生点、目标和路线可达。
4. 让移动类型到地形成本使用数据表，不按单位名称分支。
5. 更新 `isWalkable`、`movementStepCost`、路径配置和必要的视线规则。
6. 在 Terrain 中使用与规则一致的可辨识材质；装饰物不能假装成不存在的掩体。
7. 测试边界、斜穿、不同移动类型、确定性和目标可达性。

深水等不可通行地形必须在输入验证阶段阻止非法出生和目标，而不是等 AI 寻路失败。

## 4. 新增静态掩体

1. 定义掩体实体或网格槽位，包括方向、容量和防护标签。
2. 将“是否占用掩体”和“掩体提供什么效果”作为权威状态。
3. AI 评分只使用已知地形和威胁，不使用隐藏敌军位置。
4. 命中计算读取统一掩体效果，不由渲染物体碰撞决定。
5. RenderFrame 只传稳定 ID、位置、方向和必要状态。
6. 测试争抢、离开、容量、侧后方攻击和掩体不存在时的行为。

当前树木、岩石和墙段已经是权威单格静态对象，并参与步行阻挡与视线；相邻槽位、容量、占用生命周期以及统一的方向性命中/发现修正已经实现。防守与高压制编组会使用直接或延迟接触快照评估和换用掩体，并保存可解释评分；扩展评分时仍不得读取未知敌军真实占用。

## 5. 新增兵种、武器或时代内容

当前已接入 `content-3` 版本化模板，默认八人步枪小队、轮式/履带平台和自行火炮通过编组、成员、平台、部件、岗位、展开规则、传感器和 fire mode 武器模板表达。扩展内容时沿用以下能力边界：

- 单位模板：移动类型、体型、感知、可用岗位、标签；
- 武器模板：目标域、射程、弹匣、换弹、射击节奏、伤害/压制模型；
- 编组模板：成员槽位、平台、条令和默认角色；
- 时代/科技内容：引用模板或修改器，不复制一套规则代码。

实施要求：

1. 外部输入只传模板 ID、持久化实体 ID 和允许的覆盖项。
2. 初始化时解析并验证引用；战斗中不依赖远程配置服务。
3. 目标选择按目标域、标签和效用，不判断 `rifleman`、`sniper` 等字符串。
4. 新武器继续使用弹匣和换弹接口；无限备用弹药是规则配置，不是删除弹药状态。
5. 成员真实减员仍由统一健康状态表示，不为英雄或高级兵种另建互斥生命体系。
6. 测试合法目标、射程边界、换弹、同时结算、时代组合和确定性。

## 6. 新增载具和乘员

载具必须分成三个概念：平台、部件、乘员岗位。

推荐顺序：

1. 定义平台 ID、移动类型、朝向、装甲面和部件状态。
2. 定义岗位能力，例如驾驶、射击、观察和指挥。
3. 由健康且在岗乘员与可用部件共同计算能力。
4. 换岗需要模拟时间，并进入哈希与检查结果。
5. 运输状态中的成员不提供地面容量或占领力。
6. 结果同时返回平台、部件、乘员健康和在场状态。

不得用“载具总血量归零，全部乘员同时死亡”作为默认模型。

阶段 3 的已确认实施边界是：目标 schema 保留多平台槽位，但首个运行时只接受一组一车；每个平台使用单格锚点和占用值，不实现旋转多格 footprint；运输只发生在 `BattleSetup` 显式配对的同势力平台与乘客编组之间。弃车乘员保持原车辆编组，只进行自卫、集结和撤离。

`VEHICLE-003` 至 `007` 已完成单平台、乘员、伤害、运输和基础合成兵种 AI 闭环。`ARTILLERY-002/003` 已完成 `content-3` 迁移、默认自行火炮、展开/收炮、直接逻辑弹丸、权威碰撞/爆炸和终止 settling；后续按 `ARTILLERY-004/005` 完成间射和观察验收。不得通过名称特判改变运输、展开或目标域规则。

### 6.1 新增地图内炮兵

炮兵实现必须按以下顺序完成，不能先接 UI 再让客户端猜测弹着：

权威集合、任务生命周期、tick 和事件由 `simulation.ts` 调度，私有状态类型放在 `internal.ts`，初始化放在 `runtime.ts`；散布公式、整数轨迹、supercover 碰撞与爆炸衰减等无状态规则提取到 `artillery.ts`。Worker、React 和 Three.js 不拥有这些状态。

1. 已把 `content-2` 武器迁移为 `content-3` fire mode，并验证展开规则、岗位/部件引用、弹道边界和功能门禁。
2. 已在平台运行时加入展开/收炮状态，阻止未收炮移动和未展开武器开火；状态、计时和取消原因进入哈希与 inspection。
3. 已让直接火力复用当前接触、射界和同时结算规则；逻辑弹丸使用稳定 ID、至少 1 tick 飞行和独立伤害意图。
4. 间接任务复制已经送达的接触快照，冻结 `observedAt`、`deliveredAt`、来源、置信度和最后已知格；禁止保存目标运行时引用。
5. 用整数公式计算情报误差，枚举并稳定排序地图内散布格，再用任务级随机键选择；inspection 输出全部公式分项。
6. 已在弹着时查询爆区权威占用，按格、平台和成员稳定排序结算；这个查询不得反向改变任务、散布或发射资格。
7. 已让普通终止等待在途弹丸，硬截止进入有界 `settling`；结果记录 trigger/final tick，终止后哈希冻结。
8. `RenderFrame` 只携带可见弹丸的紧凑位置，事件记录部署/任务/弹着事实，任务详情只走本方按需 inspection。

必须包含两个成对负例：只改变未发现敌军真值时，发射前任务/散布/哈希不变；只改变合法快照的年龄、来源或置信度时，误差分项按设计变化。地图外炮击不得伪装成不可见平台复用此流程。

### 6.2 新增悬停空军

空军继续复用平台、部件、岗位、传感器和武器模板，但必须把地面占用与空中安全间隔分开。推荐顺序：

1. 先加入 `hover` 移动类型、`flightRule`、显式初始高度带和权威量化离地高度，并同步 setup 迁移、克隆、验证、内容哈希和状态哈希。
2. 水平飞行可以复用编组级路径/任务，但地表成本、地面阻挡、地面占用和掩体不得被当作空中容量；同高度带用模板安全半径解决出生与移动冲突。
3. 视线端点使用权威空中高度；目标适配同时检查 `TargetProfile` 与 `ground|air` 域，禁止仅因目标仍是 `platform` 就让地面武器攻击空军。
4. 空中编组和车内乘客一样不提供地面占领力，但两者的状态与原因必须分别表达，不能复用 `passenger` 位置伪装飞行。
5. 高度切换必须是有 tick 的模拟动作并进入哈希；AI 只能依据地形、合法接触和公开目标评估高度，不能读取隐藏敌方防空武器真值。
6. `RenderFrame` 只投影当前可见高度和位置，inspection 返回本方完整飞行状态，`BattleResult` 保存最终高度带/离地高度；客户端只做插值。

`AIR-001` 实现固定高度带的无武装观察直升机和必要目标域，`AIR-002` 已实现通用高度动作、低空净空和有限情报高度效用。武器、迫降/坠毁、悬停无人机差异与完整观察验收按 `AIR-003` 至 `AIR-004` 继续，不能用名称特判抢跑。

## 7. 新增战斗模式或目标类型

1. 在 `BattleModeSetup` 增加有明确 `kind` 的判别分支。
2. 验证参与势力、目标、时限、出生和可达性。
3. 在运行时建立模式专属状态，不把模式字段散落到不相关实体。
4. 明确 AI 在无敌情、直接接触和高压制情况下是否仍推进任务。
5. 用纯函数实现目标进度或计分规则。
6. 定义所有终止原因、胜者和平局语义。
7. 将目标摘要放入 RenderFrame，转移放事件，详细原因放 inspection。
8. 添加至少一个能运行到成功终止的默认地图长程回归。
9. 验证既有模式状态哈希与结果没有变化。

防守模式曾出现“进攻方在圈外永久交火，目标进度始终为零”的问题。模式测试不能只验证目标存在，必须验证 AI 实际完成或明确失败于任务。

## 8. 多势力、同盟与中立

1. `BattleSetup` 已将固定两势力元组升级为数组，并引入版本化关系矩阵；后续扩展沿用该契约。
2. 关系必须对称或明确支持有向语义，验证器拒绝缺失和自相矛盾配置。
3. 目标选择只考虑敌对关系；中立和同盟仍参与空间阻挡。
4. 每个势力拥有独立知识库。
5. 盟友情报通过消息复制历史观察，并有独立延迟，不能共享 `Map` 引用。
6. 终止条件按模式所需敌对集合计算，不能因为中立方存活而阻止结束。
7. 友军伤害保持关闭，但射线阻挡规则必须有场景测试。

需要覆盖三方混战、中立存续、盟友延迟、关系不完整和多个胜者。

## 9. 增援与撤离入口

1. 输入包含预设入口、批次、到达 tick 和归属势力。
2. 增援不是复活，必须使用新的或外部持久化实体 ID。
3. 入口被占用时使用等待队列、替代入口或失败策略，规则需显式。
4. 未进入地图的单位不参与感知、占领、容量和伤亡统计。
5. 每次入场和无法入场都产生可解释事件。
6. BattleResult 能区分未部署、已部署、撤离和失散。

## 10. 英雄与能力

1. 能力使用通用触发、条件、目标和效果模型。
2. AI 根据可见上下文计算效用，不按英雄名字写特殊逻辑。
3. 主动能力也由 AI 使用；当前玩家不能手动施放。
4. 冷却、层数、光环来源和持续时间属于权威状态并进入哈希。
5. 英雄可以是独立编组或编入小队，但健康与在场状态保持统一。
6. 外部持久化 ID 必须出现在最终结果中。

## 11. 新增事件或 Worker 消息

### 领域事件

- 在 `BattleEvent` 判别联合增加类型。
- 事件序号在同 tick 内稳定递增。
- 明确事件是瞬时事实还是应该另有当前状态投影。
- 更新 EventFeed、ShotEffects 等相关消费者和穷尽处理。
- 测试事件字段、顺序和只产生一次的约束。

### Worker 消息

- 只有线程边界出现新交互时才增加命令；纯 UI 状态不需要 Worker 消息。
- 命令和响应必须带 `sessionId`。
- 输入在 Worker 内再次钳制或验证。
- 高频消息评估大小，详情优先按需请求。
- 测试切换会话后旧消息不会污染新状态。
