# 工程约束与架构不变量

> **文档角色**：确定性、权威状态和模块边界的工程规范
> **权威性**：规范性约束；偏离需要显式架构决策
> **何时阅读**：修改模拟、权威状态、随机、哈希、情报、契约、线程边界或性能时
> **可跳过**：不涉及上述内容的纯文档、文案或局部 CSS 改动
> **相关代码**：`src/sim`、`src/worker`、`src/client`，边界规则也约束 `render/ui`

本文是开发阶段的规范性约束。关键词“必须”“不得”表示合入前必须满足；“应”表示默认选择，偏离时需要在变更说明中给出理由。

## 1. 真相来源

战斗模拟是唯一权威来源：

- 地图通行、感知、情报、移动、射击、伤亡、士气、占领和胜负必须在 `src/sim` 中结算。
- `RenderFrame` 是适合高频传输的只读投影，不是完整存档。
- `BattleEvent` 描述已经发生的事实，不能被客户端重新解释为另一种结果。
- `EntityInspection` 是按需调试和观察数据，不得成为 AI 输入。
- Three.js 动画、粒子、插值和 UI 状态不得反向修改模拟。

未来城市建造和养成系统应通过版本化战斗输入创建 `BattleSetup`，战后只消费 `BattleResult`。它们不得直接持有或修改战斗运行时对象。

## 2. 确定性

相同规则版本、输入、seed 和 step 数必须得到相同状态哈希与结果。

### 2.1 时间

- 模拟固定 `20Hz`，一 tick 的规则含义不能依赖设备帧率。
- 只有 `BattleSimulation.step()` 能推进权威状态。
- Worker 的真实时间只负责决定调用多少次 `step()`；真实时间不进入模拟。
- 暂停、切换标签页或渲染卡顿不能跳过规则步骤。

### 2.2 随机

- 模拟禁止使用 `Math.random()` 和系统时间。
- 随机值必须由战斗 seed、稳定实体 ID、tick 和稳定序号推导。
- 不得通过新增一次随机调用改变同一 tick 中其他实体的随机结果。
- 随机流命名应表达用途，例如地图高度、命中或伤情，而不是使用共享全局序列。

炮兵至少使用互不串扰的 `artillery-scatter-cell`、`blast-member-effect` 和 `blast-platform-effect` 键。散布键由稳定任务/武器/射击序号组成；爆炸效果键由 projectile ID 与目标实体 ID 组成。弹道和碰撞本身不随机，禁止为它们消耗随机值，也禁止用一个可变全局“第 N 发炮弹”序列作为随机源。

### 2.3 顺序

- 影响结果的集合必须使用稳定 ID 或明确比较器排序。
- 不得依赖对象属性、`Map` 或 `Set` 的偶然构造顺序来决定目标、伤害或移动优先级。
- 同 tick 的互相伤害应先收集意图，再按稳定顺序结算，避免遍历先后决定谁能射击。
- 新增冲突解决规则时，平局处理必须显式且可测试。

### 2.4 数值

- 概率、士气、压制和占领进度优先使用整数基点 `0..10000`。
- 网格坐标、tick、弹药和成员计数使用整数。
- 浮点数主要用于渲染位置；若浮点结果参与权威决策，必须固定舍入方式并补跨运行测试。

## 3. Tick 管线

当前每 tick 顺序如下：

1. 更新增援入口与部署。
2. 推进乘员换岗、派生平台能力并结算此前已失效的飞行平台。
3. 推进运输上下车动作。
4. 送达已排队情报。
5. 更新本地感知。
6. 更新 AI 决策。
7. 推进或建立悬停平台高度动作。
8. 评估、建立或推进间接火力任务。
9. 推进平台展开与收炮。
10. 推进移动与占用。
11. 按当前位置与来源状态刷新持续光环应用。
12. 按稳定来源、能力和友军候选顺序评估主动能力，成功使用后结算效果、次数与冷却。
13. 推进已有逻辑弹丸，生成本 tick 射击/新弹丸，并共同结算弹着与即时射击意图。
14. 更新压制和士气。
15. 处理撤离。
16. 更新目标区。
17. tick 加一。
18. 判断终止条件。

顺序本身属于规则。调整它可能改变射击资格、占领力量和终止 tick，必须：

- 新增覆盖受影响先后关系的场景测试；
- 重新验证固定 seed 的状态哈希；
- 判断是否需要升级 `rulesVersion`。

### 3.1 炮兵接入顺序

`ARTILLERY-002` 已在 AI 决策后、移动前推进平台展开/收炮。`ARTILLERY-003` 起在移动后先推进本 tick 开始前已经存在的逻辑弹丸并收集命中意图，再生成本 tick 的即时射击意图和新弹丸，最后把两类伤害按稳定顺序共同结算。约束如下：

- 本 tick 新创建的弹丸最早在下一 tick 命中。
- 本 tick 到达的弹丸和本 tick 合法生成的即时射击同时结算，不能因遍历顺序阻止后者开火。
- 刚完成收炮的平台可以在同 tick 开始移动；刚完成展开的平台可以在同 tick 进入瞄准/开火资格。
- 情报必须先送达、再更新感知、再建立任务，因此同 tick 新送达的历史快照可参与本 tick 决策；本 tick 开火暴露最早影响之后的感知更新。
- 普通终止候选等待在途弹丸；硬截止先记录 termination trigger 并进入 `settling`，该阶段只在弹丸结算前刷新持续光环来源，不再评估或使用主动能力，再执行弹丸推进、影响结算、tick 增加和最终冻结。

炮兵接入后的完整顺序属于 `stage-3.8` 规则，不能在实现时为了复用现有函数而交换任务、弹着、发射或伤害结算先后。

`stage-4.2` 的平台伤害仍先在同 tick 完整收集并按稳定 ID 结算；全部部件状态刷新后，飞行失效再按平台 ID 依次解析为迫降或坠毁。该步骤不得在单个命中意图中提前执行，否则同时伤害、落点占用和事件顺序会依赖遍历先后。

## 4. 状态与哈希完整性

新增权威状态字段时必须逐项确认：

- 输入验证和默认值；
- `cloneSetup` 或等价深拷贝；
- 运行时初始化；
- 必要的 `RenderFrame`、事件、检查或最终结果投影；
- `getStateHash()`；
- 确定性和终止后冻结测试。

哈希必须包含所有会影响未来决策或最终结果的状态，包括延迟消息、AI 目标、移动预约、冷却、进度和稳定窗口。纯表现状态不得进入哈希。

炮兵新增的展开状态/剩余 tick、任务快照与评分、任务内序号、瞄准进度、误差半径/偏移、逻辑弹丸、发射/命中 tick、效果快照、终止 trigger 和 `settling` 状态都必须进入哈希。弹丸的纯渲染插值坐标从这些字段派生，不重复存储，也不进入哈希。

空军新增的 `airborne|forced-landed|crashed` 状态、高度动作、合法攻击机会和候选评分必须进入哈希；迫降/坠毁落点、平台静态占用与乘员地面占用只由稳定格序和同 tick 完整损伤结果决定。

`ABILITY-001` 的被动修正完全由已哈希内容、成员模板引用和现有健康/在场状态派生，不重复保存运行时能力状态。`ABILITY-002` 的活动光环应用保存稳定来源/应用 ID、目标、距离、开始 tick 和实际生效效果，按应用 ID 排序后进入哈希；位置和来源状态改变后只在固定刷新阶段替换集合。`ABILITY-003` 的主动能力状态保存稳定 ID、来源、模板、剩余次数、冷却截止 tick、使用序号、最近使用 tick，以及含候选分项和拒绝原因的最近评估；这些字段按来源成员和能力 ID 排序后全部进入哈希。后续层数或持续状态同样必须建立显式来源状态并按本节完整覆盖。

## 5. 有限情报

- 真实敌军状态与势力知识必须分离。
- AI 追踪敌军时只能使用直接接触或 `ContactState.lastKnown`。
- 情报延迟按模拟 tick 计算，暂停时不送达。
- 同盟共享未来也必须发送带观察时间和送达时间的历史快照，不能共享实时引用。
- 调试视图可以全知，但不得复用为 AI 上下文。

任何新增 AI 查询都要回答：该单位为什么在这一 tick 知道这件事？无法回答时视为情报泄漏。

## 6. 数据契约和版本

边界契约包括：

- `BattleSetup`：外部系统到战斗；
- `WorkerCommand` / `WorkerMessage`：主线程与 Worker；
- `RenderFrame` / `BattleEvent` / `EntityInspection`：观察端；
- `BattleResult`：战斗回到城市、养成和世界系统。

规则：

- 所有外部输入在创建运行时状态前验证，错误应尽早失败。
- 判别联合新增分支时，消费端使用穷尽处理或明确降级行为。
- 只添加可选字段且有确定默认值时可以保持 schema 版本；改变字段含义、单位、必填性或结果语义时必须升级版本。
- `schemaVersion` 表示数据结构，`rulesVersion` 表示同一输入的结算语义，两者不得混用。
- 未来持久化数据需要迁移函数；不得让 UI 猜测旧版本结构。
- ID 在一次战斗和最终结果中必须稳定、唯一，并能够映射回外部持久化实体。

## 7. 模块边界

### 7.1 `src/sim`

- 必须可在 Node.js 中无 DOM 运行。
- 只导出 `src/sim/index.ts` 中声明的公共 API。
- `internal.ts` 只供模拟实现使用，浏览器层不得导入。
- 规则优先提取为小型纯函数；大型调度保留在 simulation 中。

### 7.2 Worker 与客户端

- Worker 拥有唯一模拟实例和运行节拍。
- 每条消息带 `sessionId`；旧会话消息必须被忽略。
- 不向主线程发送完整运行时状态或函数。
- 高频帧保持紧凑，低频详情使用按需检查。

### 7.3 渲染与 UI

- 只消费公开投影，不复制命中、占领或胜负规则。
- 动画允许抽样和丢帧，但不能改变事实顺序。
- 创建的 Three.js 几何体、材质和纹理必须在生命周期结束时释放。
- 大量同类实体优先实例化，避免一名士兵对应完整 React/Three 对象树。
- 固定工具栏、面板、标记和网格使用稳定尺寸，动态文字不得推动核心布局。
- 图标按钮必须有可访问名称；桌面与窄屏都要验证无溢出和遮挡。

## 8. 领域规则不变量

- 小队负责主要 AI，成员负责真实伤情、武器状态和最终结果。
- 健康 `healthy/wounded/incapacitated/dead` 与在场 `deployed/evacuated` 是两条轴。
- 死亡和失能不是撤离；撤离也不能抹除健康结果。
- 当前不允许复活、投降和友军伤害。
- 飞行中的空军不占地面容量，也不能自动获得地面占领力；迫降或坠毁后平台残骸与已下车乘员按普通地面占用分别登记。
- 空中高度带、量化离地高度和移动预约属于模拟权威状态；渲染高度不能反向成为视线、容量或目标域事实。
- 高度切换必须保存源/目标带、量化离地高度和剩余 tick；动作期间占用经过的全部高度带，AI 只能依据合法接触、公开任务和地形评分。
- 直接射击必须同时满足武器目标域、效果适配与权威三维射程；高度 AI 的攻击分项只能读取本方武器和合法接触快照。
- 载具能力未来由平台、部件和乘员岗位共同决定，不使用一条总生命值替代。
- 玩家观察和暂停不影响 AI 决策，也不进入状态哈希。

## 9. 性能约束

- 优先保持行为正确和可复现，再优化热点。
- AI、视线和寻路不得无条件对所有实体执行每 tick 全量两两比较。
- Worker 当前最多追赶 4 tick，每 2 tick 发布一个渲染帧；修改这些值不应改变模拟结果。
- 未来协议压缩不得丢失实体 ID、事件顺序或检查能力。
- 性能基准使用固定场景并同时比较最终哈希。
- 大型规模上线前必须记录模拟 tick P95/P99、Worker 消息体积、主线程帧时间和内存增长。
- 当前中型/大型固定场景、参考设备基线和降级门槛以 `13 §9` 为准；不同设备的结果不得直接混作优化前后对比。

## 10. 当前限制

以下是当前实现限制，不应被误当成长久设计：

- 独立演示生成器的无参默认值仍为两个势力；网页演示通过显式 `DemoBattleSetupOptions` 生成三方关系场景；Worker 和模拟入口只接收完整 `BattleSetup`；
- `content-9` 当前启用默认八人步枪小队、带队列纪律来源的小队、带集结号令持续光环的指挥小队、带“稳住阵脚”主动压制恢复的支援小队、轮式/履带平台、一组自行火炮、无武装观察直升机、武装直升机和侦察无人机，并提供空地、空空和防空武器模板；岗位、平台武器、方向装甲、部件/乘员受击、弃车、显式配对运输、炮兵展开、悬停高度动作及被动/光环/主动能力已接入，尚无维修、持续起火和复杂内部几何；
- 地图、寻路和运行时已有步行、轮式和履带移动矩阵、车辆高差阈值及八向转向；每个车辆编组最多一车，尚无多平台编组和两栖移动能力；
- 生成器尚未生成道路；
- setup schema 为 `stage-4`、rules 为 `stage-4.2`、内容为 `content-9`、地图为 `map-2`；`stage-2`/`stage-2.1`/`stage-2.2`、`stage-3.0` 至 `stage-3.8`、`stage-4.0`、`stage-4.1/content-4`、`stage-4.2/content-5`、`content-6`、`content-7` 和 `content-8` 输入已有显式迁移器；
- `simulation.ts` 已提取运行时初始化、稳定排序和无状态战斗计算，但仍拥有 AI、感知、移动、射击结算与终止等有状态调度；后续只按经过黄金哈希验证的规则域渐进拆分；
- 地图内炮兵展开、直接/间接逻辑弹丸、有限情报任务、确定性散布、碰撞/爆炸、终止 settling 和公开观察投影已实现；
- 悬停空军已有观察/武装直升机与侦察无人机编组、高度动作、低空净空、侦察/攻击高度效用、三维直射距离、迫降/坠毁和完整观察验收，尚无固定翼任务；
- 主前端包存在超过 500KB 的构建提示。

扩展这些限制时遵循 [扩展手册](./12-extension-playbook.md)，不能只放宽验证器而不补齐规则、投影和测试。
